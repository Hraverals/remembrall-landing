# 발표 대본 자료 — REMEMBRALL

장별로 대본을 쓸 때 고를 수 있는 근거·수치·설명 재료입니다. 덱의 발표자 노트와 같은 내용입니다.

## 1 · 표지

### 이 장의 역할
- 팀·서비스 이름 소개. 다음 장부터 흑백(바랜 기억) → 9번에서 색이 돌아오는 흐름의 시작점

### 들어갈 정보
- 소속: 카카오테크캠퍼스 충남대학교 3팀 '파워레인저'
- 팀원: 남준혁(팀장·PM) · 김동희(FE 리드) · 서민규(BE 리드) · 김종훈(AI 리드) · 김에스더(플래너) · 박정현(메이커)
- 서비스명: REMEMBRALL
- 한 줄 소개(README): "저장만 하고 잊어버린 콘텐츠를, 필요한 순간에 AI가 대신 꺼내 주는 앱"
- 한 줄 정의(조사 자료): "저장만 해두고 잊어버리는(Save & Forget) 숏폼 북마크 문제를 AI 자동 분류와 위치 트리거 알림으로 해결하는 능동형 아카이빙 비서"
- 앱 첫 화면 문구: "저장만 해두고 잊은 곳, 근처에 가면 다시 꺼내드릴게요"

### 아이콘 의미 (Figma C안 「떠오르는 계단」)
- 바랜 카드 두 장 뒤로 선명한 카드 한 장이 계단처럼 떠오르는 모양
- 작고 흐린 것 = 잊힌 기억 → 크고 또렷한 것 = 다시 꺼낸 기억
- 런처 아이콘·알림 글리프·홈 화면 크기용으로 설계, 라운드는 짧은 변의 22%
- 로고 시안은 A(바랜 사진) · B(가까워지면 또렷한 점) · C(접어 둔 귀퉁이) 세 방향을 탐색한 뒤 「떠오르는 계단」으로 확정

### 디자인 콘셉트 '바랜 기억'
- 저장한 지 오래될수록 썸네일이 바래고(오늘 0% → 3주 30% → 5개월 50%), 근처에 오면 원래 색으로 돌아옴
- 발표 흐름도 같은 은유: 문제 파트 흑백 → 솔루션부터 컬러

### 선택 자료
- 이름 유래 후보: 해리포터의 '리멤브럴'(주인이 뭔가 잊으면 연기가 붉게 변하는 유리구슬). 레포 문서에 근거 없음 — 팀 확인 후 사용

### 시간
- 약 15초

## 2 · 목차

### 이 장의 역할
- 발표 순서 안내. 생략하거나 5초 안에 넘겨도 되는 장

### 순서와 각 파트의 한 줄 요지
- 01 배경: 정보는 숏폼에서 찾고, 저장·공유는 이미 습관이다
- 02 문제: 저장한 것의 대부분은 다시 열리지 않는다(저장 후 방치)
- 03 솔루션: 공유 한 번 → AI가 장소 정리 → 근처에서 먼저 꺼내 줌
- 04 기술: 장소 확정, 지오펜스 재조회, 꺼내기 에이전트, LLM 평가, 실패 설계
- 05 차별화: 정리 + 근처에서 먼저 꺼내기를 함께 하는 서비스
- 06 로드맵·BM: 장소 → 시간 → 함께, 방문 직전 순간 기반 BM
- 07 팀 소개 / 08 시연 영상

### 시간
- 5~10초

## 3 · 숏폼, 새로운 검색창

### 이 장의 역할
- "왜 하필 숏폼인가" — 사람들이 장소 정보를 숏폼에서 찾는다는 전제

### 화면 구성
- 도넛 2개: 40% / 47% (서로 다른 조사의 단일 비율, 합계 아님)

### 핵심 수치와 출처
- 40%: Z세대(18~24세) 약 40%가 맛집 등 일상 정보를 찾을 때 구글 검색·지도 앱 대신 틱톡·인스타그램을 먼저 사용
  · Google 수석부사장 Prabhakar Raghavan, Fortune Brainstorm Tech 컨퍼런스 발언(2022, Google 내부 데이터)
  · 보도: tech.co/news/google-gen-z-tiktok-instagram-search
- 47%: 소비자가 가장 주목하는 숏폼 유형 1위 = 특징을 핵심만 전달하는 '정보성 콘텐츠'(47%)
  · CJ메조미디어 「2026 디지털 라이프스타일 리포트: 숏폼 광고 소비자 인식 조사」(2026.06)
  · lib.mezzomedia.co.kr/newsletter/202606/01_MezzoMedia_2026_Digital_Lifestyle_Report_Shortform.pdf

### 보강 수치 (필요 시)
- 매일 숏폼을 보는 유저 80.6%, 식음료(맛집) 관심도 63% 이상 (픽플리, 2026.04)
- 숏폼으로 '새로운 정보 발견' 30.3% (픽플리)
- 숏폼을 보는 이유 = 몇 초 만에 가치 있는 정보인지 스스로 판별(Fast-Filtering) 가능, 서론 없이 비주얼·분위기만 보여줌

### 인지과학 지표 (원 출처 검증이 약함 — 쓸 경우 '알려진 지표' 정도로)
- 인간 뇌는 시각 정보를 텍스트보다 약 6만 배 빠르게 처리, 뇌로 들어가는 정보의 90%가 시각 정보 (3M·MIT 인용 지표)
- 1분 영상 ≈ 180만 단어(웹페이지 3,600개 분량) (Forrester Research, James McQuivey)
- 기억 유지율: 영상 95% vs 텍스트 10% (3일 후, Insivia)

### 다음 장 연결
- 숏폼으로 찾은 정보를 사람들은 어떻게 처리하나 → 저장·공유 습관

### 시간
- 약 25초

## 4 · 저장 · 공유 · 재검색

### 이 장의 역할
- 숏폼을 '저장'하고 '공유'하는 행동은 이미 습관 → 우리 앱 진입점(공유 버튼)이 새 행동이 아니라는 근거
- 동시에 '재검색'이라는 불편(이중 노동)을 보여줌

### 화면 구성
- 가로 막대 3개(0~100% 기준): 저장 73.4% / 공유 79.5% / 재검색 62.6%
- 재검색 막대만 회색 톤을 다르게 = 불편 지점

### 핵심 수치와 출처 — KT 나스미디어 「2026 인터넷 이용자 조사(NPR) — 숏폼 편」(2026.04)
- 숏폼을 나중에 다시 보려고 '저장'한 경험: 20대 73.4%, 10대 69.9%
- 숏폼을 지인·외부로 '공유'한 경험: 20대 79.5%, 10대 78.5%
- 숏폼 시청 후 위치·상세 정보가 궁금해 별도로 '추가 검색'한 비율: 62.6%
- blog.nasmedia.co.kr/entry/2026NPRusersurveyinsight-1shortform

### 해석 포인트
- 저장·공유 = 10초 안에 일어나는 익숙한 동작 → 사용자에게 새 습관을 요구하지 않음
- 공유 79.5% → REMEMBRALL은 OS 공유 시트(공유하기 버튼)에서 시작. 앱을 따로 열 필요 없음
- 재검색 62.6% → 숏폼 자체만으로는 지도·일정 정리가 안 됨 → AI가 장소를 대신 찾아 확정(기술 파트 '장소 확정'으로 연결)

### 다음 장 연결
- 저장은 쉽게 한다 → 그런데 그다음은?

### 시간
- 약 30초

## 5 · 즉시 행동 vs 나중에

### 이 장의 역할
- 좋은 정보를 봐도 바로 행동하지 않는다 = '나중'에 의존하는 구조

### 화면 구성
- 세로 막대 2개: 즉시 행동 8.4%(회색) / 나중에 확인 97%(검정)

### 핵심 수치와 출처 — 픽플리(Pickply) 「숏폼 콘텐츠 마케팅 소비자 경험 리포트」(2026.04)
- 숏폼으로 유용한 정보를 얻은 뒤 즉시 행동(방문·구매 등)으로 옮기는 비율: 8.4%
- '추후 재확인' 과정을 거치는 비율: 97%
- 일일 숏폼 시청률 80.6%, 새로운 정보 발견 30.3%
- pickply.com/blog/short-form-content-marketing-consumer-experience

### 주의
- 8.4%와 97%는 별개 문항 → 합이 100%가 아님. '둘 중 하나' 구도로 말하지 말 것
- 안전한 표현: "바로 행동하는 사람은 8.4%뿐, 97%는 다시 확인하는 과정을 거친다"

### 해석 포인트
- 장소가 실제 방문으로 이어지려면 '나중'이 제대로 와야 함
- 판별·저장은 10초 만에 일어나지만, 실행은 미뤄짐 → 미뤄진 정보를 다시 꺼내 줄 장치가 필요

### 다음 장 연결
- 그 '나중'은 실제로 오는가? → 대부분 오지 않는다

### 시간
- 약 20초

## 6 · 저장 후 방치

### 이 장의 역할
- 문제의 핵심 수치: 저장한 것의 대부분은 다시 열리지 않는다(Save & Forget)

### 화면 구성
- 큰 숫자 85% + 100칸 격자(진한 15칸 = 다시 봄, 연한 85칸 = 방치)

### 핵심 수치와 출처
- 소셜 플랫폼(인스타·틱톡·유튜브) 전반의 저장 → 실제 재열람 전환율(Saved-to-viewed) 15% 미만 = 85% 이상 방치 (추산)
  · Rana, 「Why users save content but never revisit it — and how platforms can fix it」(Medium Product Research, 2026.04)
  · 같은 글에서 '귀환 시스템(Return System)'의 부재를 원인으로 지적
- 나중에 보기(Read-it-later)·북마크 앱 실측: 저장 콘텐츠의 83%는 끝내 소비되지 않음, 헤비 유저일수록 재열람률 12%까지 하락, 북마크의 65~88% 미열람
  · Media Tsundoku (Mozilla Pocket 등 Read-it-later 데이터 인용), mediatsundoku.com
- 요약표 표기: '저장 후 방치 83%~85%'

### 해석 포인트
- 판별·저장은 10초, 그러나 저장한 정보의 80% 이상은 영원히 방치
- 100개 저장 → 85개는 다시 안 열림
- 격자의 흐려지는 칸 = 앱 디자인의 '바랜 기억'과 같은 은유

### 주의
- 추산·인용 데이터 → "약 85%", "10개 중 8개 이상"처럼 범위로 말하는 게 안전

### 다음 장 연결
- 왜 다시 안 볼까? → 두 가지 원인

### 시간
- 약 25초

## 7 · 다시 보지 않는 이유

### 이 장의 역할
- 방치의 원인 2가지 → 이후 솔루션이 각각 어떻게 해결하는지의 기준점

### 화면 구성
- 아이콘 2개 + 키워드: 분류 부재(디지털 잡동사니 서랍) / 리마인드 부재(체크박스 효과)

### 원인 1 — 분류 부재: '디지털 잡동사니 서랍(Digital Junk Drawer)'
- 맛집·요리·운동·여행 등 모든 카테고리의 릴스·쇼츠가 시간순 썸네일로 뒤섞여 쌓임
- 다시 찾으려면 스크롤하며 뒤져야 함 → 다시 보지 않는 이유 1위(설문)
- 출처: Design Bootcamp(Medium), 「Rethinking Instagram Saved: Driving more revisits to saved content」(2025.09)
  medium.com/design-bootcamp/rethinking-instagram-saved-driving-more-revisits-to-saved-content-d368c30009f2

### 원인 2 — 리마인드 부재: '체크박스 효과(Checkbox Effect)'
- 저장 버튼을 누르는 순간 뇌가 과업을 끝냈다고 착각 → 저장했다는 사실 자체를 잊음
- 다시 보지 않는 이유 2위(망각) — 같은 Design Bootcamp 설문
- 디지털 호딩(저장만 쌓이는 현상)과 연결
- 출처: UC Berkeley School of Information, 「ScrollWise: AI-Driven Learning Retention Strategies」
  ischool.berkeley.edu/sites/default/files/scrollwise_product-report_vf_1.pdf

### 솔루션과의 대응
- 분류 부재 → AI가 영상 속 장소를 추출·검증해 지도/근처 목록으로 정리
- 리마인드 부재 → 그 장소 근처에 가면 앱을 열지 않아도 먼저 알림
- 핵심 문장 재료: 문제는 '저장'이 아니라 '다시 꺼내는 순간'이 없다는 것

### 다음 장 연결
- 검은 화면 질문: "그 장소, 지나갈 때 기억나셨나요?"

### 시간
- 약 30초

## 8 · 그 장소, 지나갈 때 기억나셨나요?

### 이 장의 역할
- 흑백 구간의 마지막. 문제를 청중 자신의 경험으로 가져오는 질문 한 줄
- 다음 장(9번)으로 페이드 전환되며 색과 로고 모션이 돌아옴

### 화면 구성
- 검은 배경 + 질문 "그 장소, 지나갈 때 기억나셨나요?"

### 연결 재료
- 앞의 원인 2(체크박스 효과)의 체감 버전: 저장했지만 그 앞을 지나가도 떠오르지 않음
- README 문제 정의: "가고 싶은 장소를 저장해 두지만, 정작 그 장소 근처에 갔을 때는 저장했다는 사실조차 떠올리지 못한다"
- 프로젝트 개요의 문제 정의: Shorts에서 장소를 발견해도 실제 방문으로 이어지지 않음 / 저장한 콘텐츠가 쌓이기만 하고 다시 확인하지 않음 / 사용자가 직접 장소명과 위치를 정리해야 함 (docs/카테켐프로젝트 개요.md)

### 진행 팁
- 질문 뒤 1~2초 멈춘 후 넘기면 전환 효과가 살아남

### 시간
- 약 10초

## 9 · REMEMBRALL 등장

### 이 장의 역할
- 솔루션 등장. 흑백 → 컬러 전환 순간

### 화면 구성
- 로고 모션(앱 실행 모션 「떠오르는 계단」과 같은 타이밍, 4.8초 반복) + REMEMBRALL + "잊은 장소를, 근처에서 다시"
- 제목·문구는 발표 모드에서 순서대로 떠오름

### 서비스 정의 재료
- README: 공유받은 콘텐츠를 에이전트가 자동으로 요약·분류하고, 적절한 상황이 되었을 때 먼저 꺼내 주는 앱
- 조사 자료 한 줄 정의: 저장만 해두고 잊어버리는 숏폼 북마크 문제를 AI 자동 분류와 위치 트리거 알림으로 해결하는 능동형 아카이빙 비서
- 사용자가 하는 일: 숏폼을 보다가 '공유' 한 번. 정리와 기억은 앱이 대신

### 핵심 가치 3가지 (조사 자료 Part 1)
- 입력의 간편화: 유튜브 쇼츠 시청 중 앱을 이탈하지 않고 공유 버튼 하나로 저장
- 데이터 구조화: 비정형 영상에서 장소 엔티티를 추출해 지도·근처 목록으로 정리
- 컨텍스트 기반 리마인드: 다시 찾아봐야 하는 저장함이 아니라, 근처에 가면 먼저 푸시 → 실제 방문으로 연결

### 색이 돌아오는 이유 (디자인 콘셉트 '바랜 기억')
- 앱 색: 아이보리 #F6F1EE(바탕), 자두색 #6B4E7A(다시 꺼낸 순간에만 칠함)
- 썸네일 바램 단계: 오늘 0% → 3주 30% → 5개월 50%, 근처에 오면 0%로 복원
- 로고 모션 의미: 흐린 뒷장들이 차례로 들림(기억을 뒤적이는 중) → 맨 앞장이 '뾱' 하고 골라짐 → 앱에서는 이 장이 근처 탭 첫 카드로 펼쳐짐 (docs/design/c-launch-motion.md)

### MVP 범위 (질문 대비)
- YouTube Shorts + 위치 기반 트리거. 일정(축제·팝업) 트리거와 Instagram은 로드맵

### 시간
- 약 25초

## 10 · 동작 방식

### 이 장의 역할
- 서비스 전체 흐름 5단계 한눈에. 이후 화면·기술 장표의 목차 역할

### 화면 구성
- 공유 → 분석 → 확정 → 대기 → 꺼내기 (꺼내기만 자두색: 앱 규칙 "자두색 면은 다시 꺼낸 순간에만, 화면당 한 곳")

### 단계별 자료
- ① 공유: OS 공유 시트로 YouTube Shorts 링크 전달. 보던 영상 위에 '저장했어요' 시트, 앱 화면 이동 없음
- ② 분석: Vertex AI Gemini가 YouTube URL을 영상 입력으로 직접 받아 3줄 요약·카테고리·장소 후보·기간 정보 추출. 다운로드·STT 없음
- ③ 확정: 장소 후보를 실제 장소·좌표로 검증. 결과 3종 = 장소 확정 / 확인 필요(후보 2~3곳 → 사용자에게 되묻기) / 장소 없음
- ④ 대기: 요약 임베딩을 pgvector에 저장, 확정 장소 중 현재 위치에서 가까운 곳만 OS 지오펜스로 등록
- ⑤ 꺼내기: 근처 도착 이벤트 → 꺼내기 에이전트가 영업·날씨·알림 이력을 보고 판단 → 가치 있을 때만 FCM 알림

### README 동작 방식 원문 (5단계)
- 공유 → 분석(3줄 요약 + 장소·일정 추출) → 트리거 설계(언제 다시 보여줄지: 위치/기간/시간대) → 대기(임베딩을 벡터 DB에 저장) → 알림(근처 도착·일정 임박 시)
- 현재 MVP는 이 중 '위치' 트리거만 구현

### 수치
- 분석 소요: 실제 Shorts 10편 평균 59초(최소 24초, 최대 189초) → 앱 문구 "보통 1분쯤 걸려요"의 근거
- 분석 비용: 쇼츠 1편 약 3,927토큰, 호출당 1원 미만(PoC)

### 저장하지 않는 것 (질문 대비)
- 영상·음성·전체 자막 저장 안 함. 원본 URL·videoId, 제목·썸네일 등 메타데이터, 짧은 요약, 검증된 장소, 위치 트리거만 저장 (docs/카테켐프로젝트 개요.md)

### 시간
- 약 40초

## 11 · 저장

### 이 장의 역할
- 저장 흐름 화면: 공유 → 분석 중 → 되묻기
- Notion UX 강조점 2개(되묻기, 오프라인 저장 큐)를 붙이는 장

### 화면 구성
- 공유(13 공유 받음) / 분석 중(03) / 되묻기(02, 자두색 테두리)

### 공유 시트
- YouTube 공유 → 앱이 앞으로 뜨고 보던 화면 위에 시트가 덮임. 별도 화면 이동 없음 (expo-share-intent)
- 상태 5가지와 문구:
  · 저장 중 "저장하고 있어요"
  · 저장 완료(201) "저장했어요 / 어디인지 찾으면 기억 탭에 넣어둘게요. 그 근처에 가면 다시 꺼내드려요."
  · 이미 저장(200) "이미 저장한 영상이에요"
  · 대기열 "저장해둘게요 / 다음에 앱을 열 때 다시 보낼게요."
  · Shorts 아님(400) "Shorts 링크만 저장할 수 있어요"
- 저장 중에는 버튼·끌기·뒤로 가기 모두 막음. "돌아가기" = 앱이 뒤로 가서 YouTube로 복귀
- 지원 링크: YouTube Shorts만. youtu.be·?si=·m.youtube.com 형식은 정규화해 같은 저장물로 처리. 일반 영상·인스타·임의 문자열은 거절

### 오프라인 저장 큐 (Notion: "공유만 하면 무조건 저장된다")
- 로그인 전·네트워크 끊김 상태의 공유도 로컬 파일(pending-saves.json)에 보관
- 같은 영상은 하나만, 최대 20개(넘치면 오래된 것부터 버림)
- 재전송 시점: 로그인 직후, 앱이 앞으로 올 때마다
- 성공·명확한 거절(4xx)은 삭제, 네트워크 오류·5xx·401은 남김
- 온보딩 중 들어온 공유는 시트 없이 큐에만

### 분석 중 화면
- 실측 10건 평균 59초(24~189초) → 문구 "보통 1분쯤 걸려요. 이 화면을 닫아도 계속 찾아요."
- 앱이 5초마다 상태를 다시 읽음
- 분석 결과는 푸시로 알리지 않고 기억 탭에서 확인(알림은 '꺼내는 순간'에만 쓰기 위해)

### 되묻기 (Notion: 틀리게 추측하지 않고 확인받음)
- 후보 2~3곳이면 "이 영상, 어디였을까요?", 1곳이면 "이 영상, 여기가 맞나요?"
- 콘텐츠당 최대 1회, 답할 때까지 다시 추측하지 않음
- 예전의 "미응답 시 상위 지역으로 자동 저장" 폴백은 실행된 적 없는 죽은 코드라 PR 리뷰에서 발견해 삭제(2026-10-30)
- 선택지 주소는 LocationIQ 주소를 한국식으로 뒤집어 표시 (예: "성심당, 대종로480번길, 은행동, 중구, 대전…" → "대전 중구 은행동 대종로480번길") — 동명 선택지 구분의 핵심
- 버튼 "{장소}으로 저장"은 받침에 따라 로/으로 자동 선택(영문 끝은 "이곳으로 저장")
- 기술과 직결: 장소 확정이 애매한 경우를 UX로 해결(16번 장)

### 화면 매핑 (질문 대비)
- 분석 중 03 / 되묻기 02·02b / 장소 없음 04 / 실패 05 / 완료 시 08 장소 상세
- 부분 성공(PARTIAL)은 화면에 드러내지 않기로 결정
- "직접 찾기"(02c·02d)는 디자인 완료, 실제 저장 연결 전

### 시간
- 약 35초

## 12 · 꺼내기

### 이 장의 역할
- 저장한 장소를 다시 만나는 화면 3가지

### 화면 구성
- 근처(01) / 지도(10b) / 장소 상세(08)
- 하단 탭: 근처 | 지도 | 기억, 첫 탭은 근처

### 근처 탭
- 헤더 "지금 {동네}" (역지오코딩에서 동·읍·면·가로 끝나는 값)
- 반경 직선 1km (서버 꺼내기 후보 반경과 같은 값)
- "지금" 카드 = 가장 가까운 1곳, 나머지는 바램 단계(최근 → 몇 주 → 몇 달)로 묶고 묶음 안에서 가까운 순
- 카드에서 장소 이름보다 "3주 전"이 먼저 보임 = 시간 라벨이 주인공(디자인 결정: 헤딩 서체 Gowun Dodum을 시간 라벨·헤딩에만 사용)
- 도보 시간: 직선거리 × 1.3 ÷ 80m/분(최소 1분), 30분 넘으면 km 표시 — 서버 계산기와 같은 계수
- 빈 상태: "가장 가까운 기억은 {N.Nkm} 떨어진 {장소}에 있어요." + 바랜 썸네일 3장
- 위치 꺼짐(06b): "위치를 쓰지 않는 중" — 동의·권한·위치 중 하나라도 없을 때

### 지도 탭
- 장소마다 가장 최근 저장 영상의 썸네일을 9:16 사진 핀으로 표시
- 바램 단계에 따라 핀 크기 40 / 26 / 22
- Figma 색 토큰으로 만든 커스텀 지도 스타일, 핀과 겹치는 가게·교통·도로 이름 숨김
- 핀 탭 → 요약 시트 → 끌어 올리면 상세
- Android 지도 라이브러리 마커 버그를 피하려 이름표를 지도당 하나만 두고 투명도로 숨김

### 장소 상세
- 바텀시트 멈춤 지점 2개(기본·펼침), 지도 탭에서는 요약 지점 추가
- 메모 칸: 장소 설명 → 영상 요약 → 숨김 순으로 채움, 태그 #줄서는 #오전 등
- "원본 영상 다시 보기"로 YouTube 복귀
- "이 장소가 아니에요" → 장소 검색으로 바꾸기
- "길 안내 시작"은 디자인만, 경로·지도 앱 연결은 미정(로드맵)

### 질문 대비
- 근처에 오면 썸네일 색이 되살아나는 연출은 디자인 확정, 목록 응답에 정보가 없어 앱에는 미구현
- 지도는 react-native-maps(Google Maps SDK)

### 시간
- 약 30초

## 13 · 알림 · 바랜 기억

### 이 장의 역할
- 서비스의 핵심 순간: 앱을 열지 않아도 근처에서 먼저 알림
- 디자인 콘셉트 '바랜 기억' 설명

### 화면 구성
- 잠금화면 알림(09, 자두색 테두리) / 기억 탭(07) / 바램 도식(오늘 · 3주 · 5개월 → 근처에서 복원)

### 알림
- 예시 문구: "3주 전에 저장한 빵집이 도보 4분 거리에 있어요" — 언제 저장했는지 + 지금 얼마나 가까운지
- 알림 문구는 꺼내기 에이전트가 생성. 규칙: 제목 짧게, 본문 1~2문장으로 '왜 지금'이 드러나게
  · "잊고 계셨던", "출근 중이시니"처럼 사용자 상태 단정 금지
  · 영업·행사 진행 여부 단정 금지
  · 다른 사람이 저장했다는 사실 언급 금지
- 서버는 제목 120자 / 본문 200자로만 자름
- 탭하면 해당 장소 상세(08)로 바로 열림. 로그인 전에 눌렀으면 온보딩 후 열림
- FCM: TTL 30분, 같은 알림 중복 표시 방지, Android 채널 '근처 알림'(저장 알림과 분리 — 하나로 묶으면 부수 알림 끄다가 핵심 알림까지 꺼짐)
- 온보딩의 약속 문구: "자주 울리지 않게 조용히 보낼게요."

### 과잉 알림 방지
- 회원 단위 2시간 쿨다운(침묵 판단도 1회로 셈), 30분 넘은 도착 이벤트는 무시
- 장소 단위 쿨다운은 장소 범위 정의 등 고려할 게 많아 MVP에서 보류
- 주의: 잠금화면 시안 문구 "같은 장소는 하루에 한 번만 알려요"는 현재 구현(2시간)과 다름. 일부 문서엔 10분으로 남아 있음

### 바랜 기억
- 썸네일 위 배경색 레이어 투명도: 저장 7일 미만 0% / 30일 미만 30% / 30일 이상 50%
- 필터·셰이더 없이 View 하나로 구현(가벼움)
- 바램은 썸네일에만 적용 — 텍스트·버튼까지 바래면 '비활성'과 구분되지 않기 때문
- 기억 탭 섹션: 이번 주 / 지난 몇 주 / 계절(올해 봄·지난해 겨울…), 12월은 다음 해 겨울로 셈
- "모두 38개 · 오래 잊은 것일수록 바래 있어요" (기억 탭 상단 문구)
- 근처에 오면 색이 돌아오는 연출은 디자인 확정, 앱에는 미구현

### 연결
- 발표 앞부분이 흑백이었던 이유 = 이 콘셉트

### 시간
- 약 30초

## 14 · 온보딩 · 권한

### 이 장의 역할
- 위치 '항상 허용'이 필요한 앱이 권한을 어떻게 설득하며 받는지

### 화면 구성
- 시작(00a) → 알림(00c) → 위치 ①(00d, 앱 사용 중) → 위치 정보 동의 시트(자두색) → 위치 ②(00e, 항상 허용) → 첫 저장 안내(00f) → 근처 탭

### 왜 이렇게 나눴나
- 앱을 닫아도 근처 도착을 알려면 위치 '항상 허용' 필수
- 처음부터 '항상 허용'을 요구하면 대부분 거절 → 이유를 먼저 보여주고 두 단계로 받음
- '앱 사용 중' 권한 없이는 '항상 허용'을 받을 수 없음 → 00d를 건너뛰면 00e도 건너뜀
- Google Play 정책상 백그라운드 위치는 사용 전 고지가 필요 → 00d·00e가 그 역할
- "나중에 할게요"를 눌러도 앱은 사용 가능, 설정에서 다시 켤 수 있음. '앱 사용 중'까지만이면 근처 알림만 꺼짐

### 화면 문구
- 00a "저장만 해두고 잊은 곳, 근처에 가면 다시 꺼내드릴게요"
- 00c "근처에 가면 알려드릴게요 / 자주 울리지 않게 조용히 보낼게요."
- 00d "위치는 저장한 곳 근처에 왔는지 확인할 때만 써요. 두 단계로 허용해요."
- 00e "마지막으로 '항상 허용'이 필요해요"
- 00f "Shorts에서 공유하면 여기에 쌓여요"

### 위치 정보 이용 동의 시트 (위치기반서비스 약관)
- OS 권한과 별도로 명시적 동의를 받음
- 3줄 약속:
  · "저장한 곳 근처에 왔는지만 확인해요 / 도착하면 그 장소와 시각만 서버로 보내요"
  · "지나온 길은 남기지 않아요 / 이동 경로나 실시간 위치는 보내지 않아요"
  · "언제든 거둘 수 있어요"
- 같은 시트를 온보딩·근처 탭(위치 꺼짐)·설정 세 곳에서 재사용
- 동의 → 서버 기록 → 그다음 OS 권한 요청. 저장 실패 시 권한 요청으로 넘어가지 않음
- 약관 버전이 바뀌면 동의 없음과 똑같이 취급하고 재동의("위치 정보 약관이 바뀌었어요")
- 철회 시: 앱이 지오펜스 전부 해제, 서버는 위치 이벤트를 실행 없이 버림. 문구 "거두면 저장한 곳 근처에 와도 알려드리지 않아요. 저장한 기억은 그대로 남아요."
- 동의·철회 시각은 멱등(첫 시각 유지)

### 로그인
- MVP는 게스트 세션: 설치 ID(보안 난수, 기기 보안 저장소)로 조용히 발급 → 로그인 화면 생략
- 세션이 끊기면 조용히 다시 받고 원래 요청을 한 번 재전송
- 한계: 앱 데이터 삭제·재설치 시 새 게스트가 되어 이전 저장물 접근 불가 → 카카오 로그인(구조 준비 완료)으로 해결 예정

### 시간
- 약 30초

## 15 · 아키텍처

### 이 장의 역할
- 전체 시스템 구성. 핵심 메시지 "저장은 파이프라인, 꺼내기는 에이전트"

### 화면 구성
- 앱 → (공유) 저장 파이프라인 → DB / 앱 → (도착) 꺼내기 에이전트 → (알림, 점선) 앱
- 오른쪽 외부 서비스: 저장 쪽(Gemini, YouTube Data API, 카카오 로컬·LocationIQ, 공공 상가·TourAPI), 꺼내기 쪽(Gemini, 기상청, FCM)

### 저장은 파이프라인, 꺼내기는 에이전트
- 저장: URL 검증 → 영상 분석 → 장소 확정 → 트리거 저장이 정해진 순서. AI가 도구를 고를 여지가 없어 에이전트가 아니라 고정 절차로 둠. 저장 쪽 LLM 호출은 영상 분석 1회뿐
- 꺼내기: "지금 이 사람에게 보여줄 가치가 있나"를 상황마다 판단해야 해서 도구 호출형 에이전트
- 에이전트·파이프라인은 DB를 직접 수정하지 않음. 저장은 Spring 서비스 계층이 담당

### 스택
- 앱: Expo SDK 57, React Native 0.86, TypeScript, Reanimated, react-native-maps, expo-location·task-manager·notifications·share-intent, EAS Build (Android 우선)
- 서버: Java 21, Spring Boot 4.1, Spring AI 2.0, JPA, Flyway(마이그레이션 21개), firebase-admin
- AI: Vertex AI Gemini(영상 분석·에이전트), gemini-embedding-001(768차원) → pgvector
- DB: PostgreSQL + PostGIS(좌표) + pgvector(의미 검색) 단일 DB

### 주요 설계 결정 (ADR)
- ADR001 Java/Spring 단일 앱: Python 분리의 명확한 이점 없음, 배포·통신 단순, 팀 숙련도. DB는 PG 하나 — MySQL+벡터DB(동기화 부담), MongoDB(관계 많아 부적합), ES 분리 기각. 재검토 조건: 검색량 때문에 응답시간 목표를 못 맞추면 분리
- ADR002 인증: JWT 대신 DB 불투명 세션 토큰(해시만 저장). 로그아웃·기기 교체 즉시 반영, 토큰 회전 동시성 문제 없음. 비용은 요청당 DB 조회 1회, 세션 30일
- ADR003 지오펜스: 가까운 N곳 + 재조회 원(17번 장)
- ADR004 임베딩: 768차원(pgvector 인덱스 한도 2,000 이하), 직접 정규화, 저장용/검색용 task_type 구분, 제목+요약+카테고리를 임베딩. 실패해도 분석 결과는 저장
- ADR005 Spring AI: 기존 모델 연결·관측 재사용. LangChain4j 기각, LangGraph4j는 다단계 분기·상태 저장이 필요해지면 재검토
- 결과 전달 FCM + 202: 에이전트 실행 시간이 일정치 않고 iOS 백그라운드 제한 → 앱엔 즉시 202, 결과는 푸시. 로컬 알림·WebSocket·폴링 기각

### 영상 분석 엔진 전환 일화
- 처음 쓰던 Elice API(OpenAI 호환)는 영상 입력 400, 다른 엔드포인트 404 → Vertex AI로 전환
- Vertex는 YouTube URL을 영상 입력으로 직접 받음 → 다운로드·STT 없음(정책 위반 위험 제거), 화면 글자·음성 모두 인식
- 기각안: 메타데이터만(음성·자막 속 장소 놓침), 다운로드+STT(정책 위반 소지, 화면 글자 못 읽음)
- 첫 검증: 영상 3,354 + 음성 350 = 3,927토큰, 1원 미만
- 모델 단종 대응: 3.6-flash 404 → 2.5 Flash → 신규 키에서 막혀 3.8-flash

### 데이터 정책
- 영상·음성·전체 자막 저장 안 함
- YouTube 원본 제목·설명·댓글 최대 30일 보관, 삭제 요청 7일 내 처리, AI 분석은 'AI 자체 분석' 표시(정책 문서 기준, 자동 삭제 스케줄러는 미구현)
- 좌표는 영구 저장이 허용되는 LocationIQ 사용(Google Geocoding은 캐싱 30일 제한)

## 16 · 장소 확정

### 이 장의 역할

- Notion 핵심 메시지: "한 번에 완성한 게 아니라 실패 사례를 하나씩 잡아가며 고도화"

### 화면 구성
- 왼쪽 실패 사례 4개 → 해결 / 오른쪽 59/59 격자(추출 장소 59곳 전부 정확)

### 사례별 자료
- 지점명 미표기: "스타벅스 강남역점"은 지도 주소에 안 나옴 → 역·랜드마크 기준점을 먼저 찾고 그 주변 상가 데이터에서 지점명 매칭. 기준점 반경 300m → "교보문고 광화문점"이 500m 이상 떨어져 1,000m로 확대
- 동명 매장: "을지로 골뱅이"가 송파에도 있음 → 공공 상가정보와 반경 100m 이름 대조로 구분
- 역 = 버스정류장: 강남·역삼·선릉역 검색 결과가 전부 bus_stop 태그 → 예외 처리
- 출입구 중복: 같은 역 출입구가 각각 등록돼 "후보 너무 많음" 오판 → 100m 안 근접 중복 병합
  · 근거: 검색어 50개 실측. 확실한 중복은 모두 200m 안(광화문역 출입구 2.8m, 롯데월드 43.9m, 홍대입구역 72.2m), 이름만 같은 다른 장소는 모두 478m 이상(광화문↔광화문역 478m, 경복궁↔경복궁역 516m) → 100m는 그 사이의 보수적인 값

### 그 밖의 실측 일화
- "CU"는 공공 데이터에 "씨유"로 등록 → 별칭 추가. 짧은 이름이라 15건 과매칭 → 편의점 분류로 먼저 좁힘
- "성심당 대전 본점"은 대전 지점 3곳이 전부 되묻기로 감 → 후보 지점명 교차검증 추가
- 카카오 검증 반경 50m → "CU 서초삼성타운점"이 제공사 간 141m 차이 → 200m로 확대

### 판정 순서
- 지점명이 있으면 기준점 경로 먼저(VWorld → LocationIQ)
- 없으면 관광지 제목 매칭 → 지역 상가 검색
- 이후 이름 불일치 제거 → 도로·동네급 결과 제거 → 시·도 다른 결과 제거 → 근접 중복 병합 → 개수로 판정
- 결과: 1건 확정 / 2~3건 되묻기 / 그 외 장소 없음. 좌표를 추측해서 채우지 않음, 트리거 0개도 정상

### 사용 API와 역할
- LocationIQ: 좌표·주소(영구 저장 허용)
- 공공 상가정보(소상공인시장진흥공단): 반경 안 실제 업소 이름 대조

- 카카오 로컬: 존재 검증. 이름·좌표는 저장하지 않고 ID만 — 반환 타입에서 아예 빼서 구조적으로 막음

## 17 · 지오펜스 재조회 (resync)

### 이 장의 역할
- 기술 강조점 2: OS 지오펜스 개수 제한을 '재조회(resync)' 구조로 해결

### 화면 구성
- 왼쪽 도식: 점선 큰 원 = 재조회 원, 작은 원 = 저장 장소(반경 150m), 가운데 점 = 현재 위치
- 오른쪽: OS 한도 막대(iOS 20 / Android 100), 해결 방식, 기각한 대안 4개

### 문제
- 앱당 지오펜스 한도: iOS 20개, Android 100개 → 저장 장소 전체 등록 불가

### 해결 (ADR003)
- 현재 위치 기준 가까운 순으로 (한도 − 1)곳 등록: iOS 19 / Android 99
- 남은 한 자리 = 재조회 원. 반경 = max(3km, 가장 먼 등록 장소 + 500m), 중심 = 현재 위치
- 재조회 원 안의 장소는 전부 등록된 상태 → 원을 벗어나는 순간 서버에 다시 물어 목록 교체
- 지역을 미리 나눌 필요 없음, Android/iOS 같은 로직
- 서버: PostGIS로 가까운 순 조회

### 기각한 대안
- 지역+장소 2단계 등록: 지역 지오펜스가 슬롯을 차지
- iOS 큰 위치 변경 감지(significant location change): Expo에서 사용 가능 여부 불확실, 플랫폼 분기
- Android DWELL(30초 머무름): 걸어서 지나가는 경우를 거의 못 거름
- 주기적 위치 폴링: iOS가 백그라운드 실행을 보장하지 않음, 배터리

### 세부 동작
- 서버에는 두 플랫폼 모두 ENTER(진입)만 보냄. 장소 EXIT는 앱 상태 초기화에만, 재조회 원은 EXIT만 사용
- 재등록 시점: 앱 시작, 포그라운드 복귀, 저장·삭제 후, 재조회 원 이탈, 위치 설정 변경
- 재부팅·앱 업데이트 후 자동 복원
- 장소별 안/밖 상태를 파일에 기억 → 집 근처 장소 때문에 앱을 열 때마다 알림이 가는 것 방지(Android는 등록 시 초기 ENTER가 오는데 이미 안이면 무시)
- 도착 보고 큐: 최대 20건, 시간 예산 12초, 실패 시 같은 이벤트 ID로 재전송
- 서버는 항상 202 즉시 응답 → 판단 결과는 FCM

### 알려진 한계 (Notion: 자체 인지)
- Android는 스쳐 지나가도 ENTER 발생 → 2시간 쿨다운을 소모해 이후 실제 방문 알림이 막힐 수 있음
- 위치 껐다 켜기·강제 종료·앱 데이터 삭제 후에는 앱을 다시 열 때까지 지오펜스가 비어 있음
- 재부팅 시 등록 소실 → 자동 복원 + 재동기화로 복구
- 앱이 꺼진 상태에서 동작하려면 '항상 허용' 필수
- 현재 빌드는 Android 전용(iOS 한도까지 설계만 맞춤)

### 시연 팁
- 모의 위치 앱은 Fused Location Provider 모의 모드를 쓰는 앱이어야 지오펜스에 반영, 삼성폰은 배터리 백그라운드 제한 확인

### 시간
- 약 45초

## 18 · 꺼내기 에이전트

### 이 장의 역할
- 기술 강조점 3: 도구 호출형 꺼내기 에이전트
- Notion 핵심 메시지: "근처 = 알림"이 아니라 "근처 + AI 판단"

### 화면 구성
- 근처 도착 → Gemini · 도구 호출(searchCandidates / checkVisitConditions) → 제안(장소·코스·영상) 또는 침묵
- 예시: 비 → 루프탑 대신 실내 카페

### 왜 에이전트인가
- 거리 임계값만으로 보내면 스팸처럼 느껴져 알림을 끄게 됨 → 서비스 가치 상실
- 목표는 "반드시 추천"이 아니라 "지금 다시 보여줄 가치가 있는가". 근거가 약하면 침묵(NO_ACTION)

### 판단 흐름
- 잠정 제안 → checkVisitConditions로 확인 → 부적합하면 searchCandidates로 대안 → 대안도 확인 → 최종 제안 또는 침묵

### 도구 2개
- searchCandidates(조건 자연어, 반경 최대 5km, 개인/공용/전체)
  · 의미 유사도(pgvector) + 위치 반경 + 공개/개인 범위를 한 쿼리로 결합
  · 이미 본 콘텐츠·장소는 서버가 SQL에서 자동 제외
- checkVisitConditions(장소 최대 3곳)
  · 요약 원문 2,000자에서 운영 기간·휴무 확인(첫 입력은 200자로 잘림)
  · 최근 7일 보낸 알림을 열어봤는지(무시 여부)
  · 기상청 초단기실황·단기예보·6시간 강수확률
- 회원 ID·트리거 정보는 서버가 주입 → 모델이 다른 사용자 데이터를 조회할 수 없음

### 예산
- 도구 호출 최대 6회, 모델 30초, 전체 90초, 도구 응답 24KB
- 첫 입력 후보: 반경 1km, 개인 10 · 공용 10 · 의미 검색 5건, 요약 200자

### 안전장치
- 필수 조건 7개: 받은 후보·ID만 사용 / 콘텐츠-장소 연결 정확 / 미확인 사실 단정 금지 / 사용자 상황 지어내기 금지 / 제안 형태 제약 / 종료·휴무·폐업과 모순 금지(+ 비·눈일 때 야외 권유 금지) / 공용 후보의 저장 관계 비노출
- 프롬프트 인젝션 방어: 영상 제목·요약 속 지시처럼 보이는 문장은 따르지 않음(평가 장면으로 검증)
- 서버 검증기: 실패·볼 수 없는 콘텐츠 제안 불가, 개인 항목은 본인 저장물만, 장소-콘텐츠 연결 실재 확인
- 제안 형태: PLACE 1곳 / COURSE 서로 다른 2곳 이상·누적 도보 30분 이하 / CONTENT 영상 1개 / NO_ACTION
- 원시 추론은 저장하지 않고 후보 검토·도구 호출·결과·판단 변경만 기록, 정확한 현재 좌표도 저장 안 함

### 서버 게이트 (에이전트 실행 전)

- 주의: 기본 설정은 stub 모드(항상 침묵). 시연 서버에서 LLM 모드 켜져 있는지 확인

## 19 · LLM-as-judge 평가

### 이 장의 역할
- 기술 강조점 4: AI 판단을 또 다른 AI가 채점하는 평가 체계
- Notion 메시지: "AI를 만들고 끝낸 게 아니라 성능을 측정함"

### 화면 구성
- 왼쪽: 버전별 BAD 판단 수(72건 중) v1 5 → v2 4 → v3 1 → v4 0
- 오른쪽: 품질 평균(5점 척도) 점 그래프 4.16 → 4.19 → 4.22 → 4.35 (축 4.0~4.4 구간 확대 표시)
- 키워드: 실패 분리 집계 / 기준 해시 고정 / holdout 6/6

### 평가 설계
- 골든셋 30장면 = 조정용 24 + 처음 보는 장면(holdout) 6. 조정용 24장면 × 3회 반복 = 72건
- 정답 분포: PLACE 12, COURSE 11, NO_ACTION 6, CONTENT 1
- '시간만 다른 쌍': 주말 저녁 vs 평일 아침, 금요일 심야 vs 저녁, 어제 저장 vs 몇 달 전 저장
- 특수 장면: 지시문 주입(인젝션), 종료된 팝업, 동의하지 않은 공용 후보 숨김
- 도구 세트 18장면: 날씨·휴무·전시 종료·최근 제안·식당 조건을 하나만 바꾼 쌍

### 채점
- 척도 1(BAD) / 3(ACCEPTABLE) / 5(GOOD), 3점 이상 통과
- BAD = 필수 조건 7개 중 하나라도 위반 또는 서버 검증 실패
- 심판 모델: Claude Sonnet(Elice 경유), 온도 0 / 에이전트: gemini-3.6-flash
- 격리된 DB + 실제 임베딩, 날씨만 고정값
- 공정성: 정답·참고 답안·채점 메모는 심판에게 주지 않음. 제안 형태 조건은 서버 검증기가 판정
- 기준 고정: 매 실행마다 평가 기준 문서의 SHA-256 해시를 결과에 기록, 문서가 없으면 실패
- 실패 분리 집계: 에이전트 실패·심판 실패·비교 불가는 품질 평균 분모에서 빼고 신뢰성 지표로 따로 셈(통계 왜곡 방지). 심판 응답 파싱 실패 시 1회 재시도
- 사람 라벨과의 일치율도 낼 수 있음(오프라인)

### 버전별 결과 (72건)
- v1 도구 없음: BAD 5, 품질 4.155, 중앙값 7.66초, 1,840토큰
- v2 도구 추가: BAD 4, 4.194, 8.12초, 3,971토큰(도구 사용 53%)
- v3 프롬프트 개선(운영 기간·휴무 비교, 사용자 상태 비단정): BAD 1, 4.222, 8.28초, 4,069토큰
- v3 도구 없음: BAD 0, 4.306, 6.97초, 2,033토큰
- v4 확인 중심 도구(채택): BAD 0, 4.352, 8.61초, 6,513토큰(도구 사용 94%), GOOD 48 / ACC 23
- holdout 6장면: v4 GOOD 6/6

### 인사이트
- v1 BAD 대부분은 '운영 종료가 적힌 팝업을 제안' + 사용자 상태 단정 문구
- BAD를 줄인 주역은 도구가 아니라 v3 프롬프트 문단
- 첫 입력을 다시 보여주기만 하는 v2 도구는 판단을 못 바꾸고 토큰만 2배
- 서버가 첫 입력에 줄 수 없는 정보(날씨, 요약 전문의 휴무, 최근 반응)를 주는 도구만 판단을 바꿈 → 도구 역할을 "후보 고르기"에서 "고른 후보가 지금 방문 가능한지 확인"으로 전환(v4)

### 도구 세트 평가 (v4, 54건)
- BAD 0, GOOD 49 / ACC 5, 확인 도구 호출률 42/42(100%)
- 조건 하나만 바꾼 6쌍 중 5쌍에서 3회 모두 판단이 바뀜(식당이 첫 입력 밖에 있는 쌍만 0/3)
- 사례: 비 확인 → 첫 입력에 없던 실내 북카페 검색 → 그 북카페도 확인 → 제안(3회 동일)
- v4 실패 1건 = 모델이 JSON 앞뒤에 백틱을 붙임 → 파서 보강

### 완결 기준
- 조정용 BAD 1 이하·실패 2% 이하, holdout BAD 0, 도구 세트 BAD 1 이하·확인 호출률 80% 이상 → 모두 통과

### 시간
- 약 45초

## 20 · 실패 · 재시도 설계

### 이 장의 역할
- 기술 강조점 5: 여러 모듈에 공통된 실패·재시도 설계 철학
- 메시지 재료: 외부 API·AI를 여러 개 엮으면 실패는 반드시 일어남 → "실패해도 멈추지 않게"

### 화면 구성
- 키워드 4개: 실패 코드 분류 / 후보별 독립 처리 / 중복 요청 무시 / 저장 큐 재시도
- 분석 성공률 막대: 1차 80% → 재시도 포함 100%
- 실패 화면(05) "영상을 불러오지 못했어요" + 다시 시도

### 실패 코드 분류 → 화면 문구까지
- EXTRACTION_API_ERROR(재시도 가능): "영상을 불러오지 못했어요 / 다시 시도하면 처음부터 찾아볼게요" + 다시 시도
- VIDEO_UNAVAILABLE: "볼 수 없는 영상이에요 / 비공개로 바뀌었거나 삭제된 영상"(다시 시도 없음)
- EXTRACTION_RESULT_ERROR: "장소를 알아내지 못했어요 / 링크는 그대로 보관해둘게요"(다시 시도 없음)
- PLACE_SEARCH / PLACE_VERIFICATION 장애: 요약은 확보 → PARTIAL, 화면엔 드러내지 않음
- 원칙: 장소 없음 = 정상 결과 / 분석 실패 = 오류 / 확인 필요 = 사용자 입력 대기 — 서로 다른 상태로 테스트

### 이 원칙이 생긴 일화
- 평가 중 1차 실패 2건을 '영상 접근 불가'로 단정 → 재시도하니 둘 다 성공
- 원인: Gemini 호출이 확률적으로 약 20~50% 실패 → 재시도 가능 코드로 통일, 권장 재시도 2~3회
- 무제한이던 외부 호출 타임아웃 설정(2026-11-02): Gemini 60초, YouTube·기상청 2/3초, 임베딩 10초

### 후보별 독립 처리
- 장소 후보 하나의 검색·검증이 실패해도 나머지는 계속 진행

### 중복 요청 무시 (멱등)
- 같은 영상은 콘텐츠 1개(UNIQUE + ON CONFLICT DO NOTHING), 같은 사용자의 같은 저장은 200으로 같은 응답
- 분석 선점: 상태를 PENDING → ANALYZING으로 바꾸는 조건부 UPDATE에 성공한 요청 하나만 Gemini 호출
- 비관적 락·Redis 분산 락은 서버 1대라 불필요, 낙관적 락은 아직 없는 행의 동시 INSERT를 못 막아 기각
- 알림도 실행당 1개(UNIQUE), 열람 처리는 여러 번 호출해도 결과 동일

### 동시성
- 저장·분석·삭제가 동시에 일어날 때의 write skew 방지: 회원 → 콘텐츠 순서로 공통 부모 행 잠금(데드락 회피). SERIALIZABLE·사후 복구는 기각
- 외부 API 호출은 트랜잭션 밖. 짧은 트랜잭션(저장+선점) → 외부 호출 → 짧은 트랜잭션(결과 저장). FCM도 커밋 이후 전송
- 분석 작업 큐: 동시 2개, 대기 100개. 넘치면 선점을 풀어 다음에 다시 집어 가게 함

### 자동 복구
- 1분마다 5분 넘게 멈춘 분석을 '재시도 가능 실패'로 바꿔 다음 저장·다시 시도 때 재처리(대기열 시간은 5분에 포함 안 함 — 멘토 리뷰 반영)
- 도착 이벤트: 실행이 실패·타임아웃이면 같은 이벤트로 1회 재실행(쿨다운만 건너뜀)

### 앱 쪽
- 공유 저장 큐(최대 20개, 자동 재전송), 도착 보고 큐(최대 20건, 같은 이벤트 ID로 재전송)
- 세션 만료 시 조용히 재발급 후 원래 요청 1회 재전송

### 시간
- 약 30초

## 21 · 경쟁 서비스 비교

### 이 장의 역할
- 유사 서비스 대비 차별점. "정리 + 근처에서 먼저 꺼내기"를 함께 하는 곳

### 화면 구성
- O/△/X 비교표 5행: 숏폼 공유 저장 / AI 장소 추출 / 지도 자동 등록 / 근처 도착 알림 / AI 알림 판단
- △ = 부분 지원·사용자가 직접 입력·설정

### 경쟁 서비스 3부류 (조사 자료)
1) 숏폼 공유 → AI 분석 → 지도/일정 매핑 (가장 유사)
- 채록(국내): "던지면 AI가 정리하는 두 번째 뇌". 릴스 공유 → AI 요약 + 장소 추출 → 지도 핀
- MapDreamy(한국어 지원): 영상 속 맛집·카페·명소 주소 인식 → 지도 핀, 저장 장소로 일자별 여행 동선·캘린더 자동 생성
- Plotline / Triply / Pintra(글로벌): 영상 텍스트·오디오·캡션 메타데이터 분석 → 여러 장소를 지도 매핑, 식당·카페·명소 자동 분류
2) 숏폼 북마크 + 리마인더
- Stash: 릴스·쇼츠·틱톡 링크 저장, 매일 정해진 개수를 홈에 다시 꺼내거나 지정 요일·시간에 리마인드. 지도 링크는 현재 위치로부터 거리 표시
- RemindLink: 링크 저장 시 리마인드 타이머 → 푸시
3) 위치·일정 트리거 생산성 도구
- Apple 미리 알림 / Google Keep / TickTick: 날짜·시간 또는 위치 도착/출발(지오펜싱) 알림 가능, 단 장소·시간을 사용자가 수동 입력

### 표 판정 근거
- 미리 알림류: 링크는 URL 첨부만(△), 위치 알림은 가능하나 장소 직접 입력(△)
- Stash: 거리 표시는 있으나 근처 도착 시 알림은 아님(X)
- 지도 저장형: 리마인드는 사용자가 여행 계획 시 앱을 직접 열어야 가치 발생(X)

### 차별점 2가지 (조사 자료 결론)
- 컨텍스트 인지형 리마인드: 기존 맛집 지도 앱은 "오늘 뭐 먹지?" 하고 앱을 다시 켜야 가치 발생. REMEMBRALL은 앱을 켜지 않아도 근처에 가면 선제적 푸시 → 저장 후 방치를 가장 근본적으로 해결
- 알림 품질: 근접만으로 보내지 않고 AI가 영업·날씨·알림 무시 이력을 보고 판단(스팸 방지)
- (로드맵) 콘텐츠 성격에 따라 공간(맛집 → 지도)과 시간(축제·팝업 → 캘린더)으로 분기 — 기존 서비스는 장소 단일 파이프라인에 집중

### 주의
- "없다"고 단정하지 말고 "조사한 범위에서는"
- 경쟁사 로고는 상표 문제로 넣지 않음

### 시간
- 약 40초

- 배터리 → 위치를 계속 추적하지 않고 OS 지오펜스 사용. 등록한 원에 들어갈 때만 OS가 앱을 깨움. 주기적 폴링은 검토 후 기각
- 위치 개인정보 → 위치기반서비스 약관 동의 별도. 이동 경로·실시간 위치는 보내지 않고 도착한 장소와 시각만 전송. 동의 철회 시 지오펜스 해제
