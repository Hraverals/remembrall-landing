재시도 가능한 실패

[시간] 약 30초 [대본] 외부 API와 AI를 여러 개 엮는 서비스라 실패는 반드시 일어납니다. 그래서 "실패해도 멈추지 않게"라는 한 가지 원칙을 모든 모듈에 적용했습니다. 분석이 실패하면 다시 시도하면 되는 실패인지, 영상이 삭제돼서 안 되는 실패인지를 코드로 나누고, 화면 문구와 '다시 시도' 버튼까지 다르게 보여줍니다. 장소 후보 하나가 실패해도 나머지는 계속 진행하고, 같은 영상이 동시에 들어와도 분석은 한 번만 합니다. 보내지 못한 공유는 큐에 남겨 뒀다가 자동으로 다시 보냅니다. 실제로 영상 분석 1차 성공률은 80%였는데, 재시도 설계로 100%가 됐습니다. [이 원칙이 생긴 실제 사례] - 평가 중 Gemini 호출이 확률적으로 20~50% 실패하는 현상 발견. 같은 영상이 1번째 실패, 3번째 성공처럼 번갈아 나옴. 처음엔 '영상 접근 불가'로 잘못 단정한 2건이 있었는데 실제로는 호출 실패 → '재시도 가능(EXTRACTION_API_ERROR)'으로 분류 정정 + 재시도 추가. 무제한이던 타임아웃도 60초로 설정. [세부 사실 — 질문 대비] - 분석 상태: PENDING → ANALYZING → SUCCESS / PARTIAL / FAILED. - 실패 코드와 화면 문구: · EXTRACTION_API_ERROR(재시도 가능): "영상을 불러오지 못했어요" + 다시 시도 · VIDEO_UNAVAILABLE: "볼 수 없는 영상이에요"(비공개·삭제), 다시 시도 없음 · 분석 불가: "장소를 알아내지 못했어요 — 링크는 보관", 다시 시도 없음 · 요약은 얻었는데 장소 검색 API만 장애 → PARTIAL - 중복 방지: 콘텐츠는 INSERT … ON CONFLICT DO NOTHING, 상태 PENDING → ANALYZING 조건부 UPDATE에 성공한 요청 하나만 Gemini 호출. - 분석 중 5분 넘게 멈춘 건은 1분마다 도는 스케줄러가 회수. - 저장·분석·삭제 경쟁 시 write skew 방지: 회원 → 콘텐츠 순서로 공통 부모 행 잠금(데드락 회피). - 외부 API 호출은 트랜잭션 밖에서, 앞뒤로 짧은 트랜잭션 두 개.
