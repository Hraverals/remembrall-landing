[시간] 약 40초 [대본] 기술 구성입니다. 핵심은 "저장은 파이프라인, 꺼내기는 에이전트"로 나눈 것입니다. 저장은 URL 검증, 영상 분석, 장소 확정, 트리거 저장까지 순서가 정해져 있어서 AI가 스스로 도구를 고를 이유가 없습니다. 그래서 안정적인 고정 파이프라인으로 만들었습니다. 반대로 꺼내기는 "지금 이 사람에게 보여주는 게 맞나?"를 상황마다 판단해야 해서, 이쪽에만 도구를 쓰는 AI 에이전트를 붙였습니다. 데이터는 PostgreSQL 하나에 PostGIS(좌표)와 pgvector(의미 검색)를 함께 써서, 위치와 의미를 한 쿼리로 찾습니다. [화살표] - 공유: 앱 → 저장 파이프라인 (POST /api/personal-saves) - 도착: 지오펜스 도착 이벤트 → 에이전트 (POST /api/location-events, 항상 202 즉시 응답) - 알림(점선): 에이전트 판단 → FCM → 앱 [주요 설계 결정 — 질문 대비 (ADR)] 1. 영상 분석을 Vertex AI Gemini로: 처음 쓰던 Elice API(OpenAI 호환)가 video 입력을 400으로 거부. Vertex는 YouTube URL을 영상 입력으로 직접 받아 다운로드·STT 없이 처리 → 정책 위반 위험도 제거. 2. 단일 DB(ADR001): 별도 벡터DB(Qdrant/ES)나 MongoDB는 두 저장소 동기화 비용 때문에 기각. 3. 에이전트·파이프라인은 DB를 직접 수정하지 않음. 결과만 돌려주고 저장은 Spring 서비스 계층. 4. 결과 전달 FCM + 202: 에이전트 실행 시간이 일정하지 않고 iOS 백그라운드 제한(약 10초)이 있어서. 로컬 알림·WebSocket·폴링 기각. 5. Spring AI(ADR005): LangChain4j·LangGraph4j와 비교 후 기존 모델·관측 체계 재사용. 그래프형 흐름이 필요해지면 LangGraph4j 재검토 조건 문서화. 6. 인증: JWT 대신 DB 불투명 세션(ADR002). MVP는 게스트 세션.
